# Lens 3 — Migration safety (JVM Room-validated vs real SQLCipher)

Date: 2026-07-30 · Auditor: Claude · Base commit: `6706500` (HEAD on `main`)
Scope: `MIGRATION_13_14`, `MIGRATION_14_15`, exported schema JSONs (`13.json`, `14.json`, `15.json`), instrumented `MigrationTest`, entity definitions touched in those two migrations. Reference: [docs/AUDIT_PLAN.md](../AUDIT_PLAN.md) § "Lens 3".

## Status: CLEAN (0 findings)

No blocker, needs-fix, or nice-to-have finding met the Lens 3 bar
("DDL that Room's JVM validator accepts but SQLCipher rejects at open time" /
"index Room expects that the migration didn't create" /
"ambiguity that would leave a real v13 install stuck at v13 with
`IllegalStateException: Migration didn't properly handle`").

The v13→v15 upgrade path, when it runs live for the first time on a real encrypted
SQLCipher DB, is structurally equivalent to what `runMigrationsAndValidate` already
covers on the JVM. Confidence is high that the live upgrade succeeds; the residual
unknown is the SQLCipher runtime itself, and that risk is minimized by the driver
choice (see notes below).

## Checks performed

1. **DDL vs entity — `media.favorite`.**
   Migration adds `ALTER TABLE media ADD COLUMN favorite INTEGER NOT NULL DEFAULT 0`.
   Entity declares `@ColumnInfo(defaultValue = "0") val favorite: Boolean = false`.
   15.json records `"defaultValue": "0"` on the `favorite` field. After migration the
   live DB's `PRAGMA table_info(media)` reports `notnull=1, dflt_value='0'`, matching
   what Room expects for v15. Fresh-install path (`CREATE TABLE ... favorite INTEGER
   NOT NULL DEFAULT 0`, per 15.json) produces the same. Match.

   Note: 14.json's `favorite` field has no `defaultValue` key and its `createSql`
   omits `DEFAULT 0`. This looks alarming at first glance, but it's just the state
   of the entity when 14.json was frozen (before the `@ColumnInfo` fix landed this
   session). Room's `TableInfo` comparator ignores actual dflt_value when the
   expected schema doesn't declare one, so `runMigrationsAndValidate(…, 14, …)`
   passes. And v14 → v15 open validation compares against 15.json (which DOES
   declare the default), which does match the live column. No user-visible drift.

2. **DDL vs entity — `person_photo`.**
   Migration DDL: `CREATE TABLE IF NOT EXISTS person_photo (id TEXT NOT NULL,
   ownerKind TEXT NOT NULL, ownerId TEXT NOT NULL, mediaBlobId TEXT NOT NULL,
   addedAt INTEGER NOT NULL, PRIMARY KEY(id))`. Column set, types, and NOT NULLs
   match 15.json's `createSql` and field list one-for-one. PK matches.

3. **Room-autogenerated index vs migration DDL — `person_photo`.**
   Entity: `@Entity(tableName = "person_photo", indices = [Index(value = ["ownerKind",
   "ownerId"])])`. Room's auto-derived index name for that shape is
   `index_person_photo_ownerKind_ownerId`. Migration creates exactly that name on
   exactly `(ownerKind, ownerId)`, non-unique. 15.json records the same. No missing
   index; no extraneous one that Room would flag as "found but not expected".

4. **SQLCipher compat of `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT literal`.**
   The app uses `net.zetetic:sqlcipher-android` (the modern driver — the entity
   import in `TrystDatabaseFactory.kt` is `net.zetetic.database.sqlcipher.…`, not
   the legacy `net.sqlcipher.…` package). That driver bundles SQLite ≥ 3.44, which
   fully supports `ALTER TABLE ADD COLUMN` with `NOT NULL DEFAULT <literal>` (the
   restriction is only on non-constant defaults, which don't apply here — `0` is a
   literal). No SQLCipher-specific rejection risk.

5. **Idempotency & re-run safety.**
   Both migrations use `IF NOT EXISTS` on the new object (`CREATE TABLE IF NOT
   EXISTS person_photo`, `CREATE INDEX IF NOT EXISTS index_person_photo_…`). ALTER
   TABLE ADD COLUMN doesn't have that guard, but Room only replays a migration once
   per version step, so it's not an issue in practice.

6. **No entity change wider than the migration DDL claims.**
   Diffing 13.json → 14.json → 15.json across every table confirmed the only
   structural changes are the two the migrations declare — `media.favorite` in
   v14, and `person_photo` (+ its index) in v15. No silent schema drift (e.g. an
   entity that gained an index but no migration to create it).

## Residual risk that Lens 3 cannot close

The single unknown Lens 3 can NOT rule out from static reading is the first real
in-place upgrade of a live encrypted DB on a real device (i.e. an install currently
sitting at v13 that's about to open with the v15 binary). The JVM
`MigrationTestHelper` runs against an unencrypted framework SQLite. If SQLCipher's
runtime were to reject any of the DDL above, JVM tests wouldn't catch it. The
mitigation from a code-only lens: item (4) above rules out the known-plausible
rejection modes. The recommendation therefore stands from the audit plan — the
`connectedDebugAndroidTest` variant of `MigrationTest` on a real emulator/device
(which DOES go through the SQLCipher factory when wired up that way, and could
easily be wired up as a small follow-up) would remove the last uncertainty.
That's tooling work, not a Lens 3 finding.
